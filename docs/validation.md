# Проверка качества алгоритмов

Инженерные регрессионные тесты уже проверяют управление данными. Для изменения сегментации и CFD нужен отдельный воспроизводимый набор данных и критерии приёмки.

## Следующий этап

1. Подготовить обезличенный набор исследований с разрешением на использование: обычная бифуркация, короткая ECA, выраженная извитость, несколько DICOM-серий, разные ориентации и spacing.
2. Для каждого хранить эталонную разметку, ожидаемую топологию, параметры и описание допустимых отклонений. Чувствительные данные в Git не помещать.
3. Сравнивать контуры и поверхности, связность ветвей, число открытых границ, качество тетраэдров. При изменении порогов смотреть весь набор, а не один удачный пример.
4. Для CFD фиксировать версию/сборку SU2, сетку, условия, шаг времени и численные настройки; проверять баланс расходов, сходимость по циклам, чувствительность к сетке и шагу времени.
5. Разделить экспериментально проверенные причины нестабильности и гипотезы. Описанная в SESSION_CONTEXT калибровка сопротивлений — гипотеза для проверки; ограничение давления само по себе не подтверждает корректность решения.

## Не подтверждено текущими тестами

- Качество сегментации на реальных исследованиях.
- Обработка произвольной ориентации DICOM.
- Совместимость с конкретной внешней сборкой pysu2 и полноценный CFD-прогон.
- Физическая достоверность TAWSS/OSI/RRT и давления.

Сейчас результат имеет происхождение (входные версии, параметры, каталог запуска) и статус качества `unvalidated`. Приложение отображает, что проверка качества ещё не выполнена. Автоматическое присвоение статуса «проверен» требует согласованных критериев и соответствующих расчётных тестов.
